# Codevia × GitHub: проект интеграции

Цель: проект в Codevia можно связать с репозиторием GitHub. Его можно скачать (clone/pull), отправить изменения одним коммитом (push) и опубликовать сайт на GitHub Pages. Всё это без нашего сервера, без хранения чужих данных и без «настоящего git» в телефоне.

## Принципы

1. **Без бэкенда.** Приложение общается с `github.com` и `api.github.com` напрямую. У нас нет сервера, через который шёл бы код или токены. App Privacy остаётся честным: данные уходят только в аккаунт пользователя и только по его действию. Политику конфиденциальности нужно дополнить разделом о GitHub.
2. **Без git-клиента в WebView.** Полноценный git (isomorphic-git) тянет pack-файлы, держит всю историю в памяти и требует CORS-прокси. Для карманного редактора это лишнее. Вместо него используем REST API GitHub:
   - скачивание — zip-архив ветки, его импорт у нас уже есть;
   - отправка — Git Data API, атомарный коммит.
3. **Ничего не теряется молча.** Перед каждым pull создаётся автоверсия в «Истории». Конфликт не перезаписывает файлы, а показывает выбор. Push никогда не делает force.
4. **Токен хранится только в Keychain.** Никогда в IndexedDB, localStorage, файлах проекта или журнале ошибок.

## Вход: OAuth Device Flow через GitHub App

Почему Device Flow:
- ему не нужен client secret, а значит, не нужен сервер;
- не нужен redirect URI;
- работает в любом WebView.

Порядок такой:
1. Пользователь нажимает «Подключить GitHub».
2. Приложение вызывает `POST https://github.com/login/device/code` с `client_id` и получает `user_code` и `verification_uri`.
3. На экране показан код вида `WDJB-MJHT`. Кнопка «Скопировать и открыть GitHub» открывает `github.com/login/device` в SFSafariViewController (`@capacitor/browser`). Там пользователь входит своим паролем, с 2FA и passkey: мы его пароль не видим.
4. Приложение опрашивает `POST https://github.com/login/oauth/access_token` с интервалом `interval` (обычно 5 с), пока не придёт токен. Ответы `slow_down`, `expired_token` и `access_denied` нужно обработать.
5. Токен сохраняется в Keychain (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, без синхронизации iCloud). Профиль берётся из `GET /user` и показывается в настройках.

Почему GitHub App, а не OAuth App:
- **Точные права.** Нужны только `Contents: read & write`, `Metadata: read`, а для Pages ещё `Pages: write`. Пользователь сам выбирает репозитории, к которым даёт доступ, при установке приложения. OAuth App со scope `repo` получает все приватные репозитории разом.
- **Срок жизни токена.** Токен действует 8 часов и выдаётся вместе с refresh-токеном. Если обновление потребует client secret, а его в приложении быть не должно, приложение просто снова пройдёт Device Flow одним нажатием. Это нужно проверить на прототипе.

Запасной вариант: вставить fine-grained Personal Access Token. Он нужен для GitHub Enterprise и для тех, кто не хочет ставить App.

Отключение (кнопка «Отключить GitHub»):
- токен удаляется из Keychain;
- даётся ссылка на `github.com/settings/apps/authorizations`, где доступ можно отозвать полностью.

## Сеть в приложении

Сейчас CSP основного документа запрещает любые запросы (`connect-src 'self'`). Это преимущество в безопасности, и мы его сохраняем:
- Запросы к GitHub идут через нативный HTTP (`CapacitorHttp.request`, уже в составе `@capacitor/core`), а не через `fetch` WebView. Это обходит CORS, который GitHub не поддерживает для `login/*`, и не требует ослаблять CSP.
- В коде есть один модуль `src/github/http.ts` со списком разрешённых хостов: `github.com`, `api.github.com`, `codeload.github.com`, `uploads.github.com`. Любой другой хост отклоняется.
- Токен подставляется только для `api.github.com`. Он никогда не попадает в предпросмотр, воркеры и журнал ошибок; заголовок `Authorization` вычищается при логировании.
- В Info.plist ATS остаётся по умолчанию (только HTTPS).

## Модель данных

К `ProjectMeta` добавляется необязательная связь:

```ts
interface GitHubLink {
  owner: string;           // "sardorcos"
  repo: string;            // "portfolio"
  branch: string;          // "main"
  baseCommit: string;      // SHA коммита, с которым синхронизирован проект
  /** Git blob SHA-1 каждого файла на момент baseCommit: path → sha. */
  baseTree: Record<string, string>;
  subdir?: string;         // если проект — подпапка репозитория (монорепо)
  pagesUrl?: string;
}
```

Ключевая идея в том, что git blob SHA-1 (`sha1("blob " + size + "\0" + bytes)`) считается локально за миллисекунды через WebCrypto. Поэтому любой файл можно сравнить с удалённым деревом без скачивания содержимого:
- `local ≠ base` → изменён у нас;
- `remote ≠ base` → изменён на GitHub;
- изменён с обеих сторон → конфликт.

Это обычное трёхстороннее сравнение. История на устройстве (снимки SHA-256) не меняется.

## Операции

### Клонировать (новый проект из репозитория)
1. Выбор репозитория: список из `GET /user/repos?affiliation=owner,collaborator&sort=pushed`, поиск, ветка через `GET /repos/{o}/{r}/branches`.
2. Скачивание `GET /repos/{o}/{r}/zipball/{branch}` (редирект на codeload) и существующий импорт ZIP с лимитами: убираем корневую папку `owner-repo-sha/`, применяем лимит размера 60 МБ и фильтр путей.
3. `GET /repos/{o}/{r}/git/trees/{sha}?recursive=1` заполняет `baseTree`. Если `truncated: true`, репозиторий слишком большой, и мы предлагаем подпапку.
4. Язык проекта определяется автоматически: `index.html` → web, `main.py` → Python, `index.php` → PHP.

### Pull (получить изменения)
1. Запрашиваем `GET .../branches/{branch}`. Если `commit.sha === baseCommit`, изменений нет.
2. Сравниваем деревья: `GET .../compare/{baseCommit}...{head}` либо новый `git/trees` против `baseTree`.
3. Скачиваем только изменённые blob-ы (`GET .../git/blobs/{sha}`).
4. Создаём автоверсию «Перед обновлением с GitHub».
5. Применяем изменения:
   - файлы, изменённые только на GitHub, принимаются;
   - файлы, изменённые только у нас, остаются;
   - конфликты показываются списком с выбором «оставить мой / взять с GitHub / открыть оба» и сравнением строк. По умолчанию ничего не перезаписывается.

### Push (отправить один коммит)
1. Сначала выполняем pull-проверку: если ветка ушла вперёд, нужно обновиться, и только потом отправлять.
2. Экран коммита со списком изменённых, новых и удалённых файлов. Галочки позволяют исключить файлы. Сообщение коммита предзаполнено, например «Update index.html, style.css».
3. Git Data API:
   - `POST git/blobs` для каждого изменённого файла, до 4 параллельно, бинарные файлы в base64;
   - `POST git/trees` с `base_tree = baseCommit.tree`; удаления передаются как `sha: null`;
   - `POST git/commits` с `parents: [baseCommit]`;
   - `PATCH git/refs/heads/{branch}` с `force: false`. Ответ 422 означает, что ветку обновили параллельно: выполняем pull и повторяем.
4. Обновляем `baseCommit` и `baseTree`, создаём ручную версию «Отправлено на GitHub · abc1234».

Альтернатива: GraphQL `createCommitOnBranch` — один запрос со встроенной защитой `expectedHeadOid`. Он проще, но ограничен размером запроса, поэтому годится для небольших коммитов.

### Новый репозиторий из проекта
`POST /user/repos`, приватный по умолчанию, затем первый push. Сценарий: «Создать репозиторий и отправить».

### Опубликовать сайт (GitHub Pages), только для web-проектов
1. Push в ветку.
2. `POST /repos/{o}/{r}/pages` с `source: {branch, path: "/"}`, если Pages ещё не включён.
3. Ждём `GET .../pages/builds/latest` и показываем ссылку `https://{owner}.github.io/{repo}/` с кнопками «Открыть» и «Поделиться».

Так получается путь «сделал сайт на телефоне → он в интернете» за одно нажатие. Это сильнейшая фича для аудитории Codevia: студентов и начинающих.

## Интерфейс

- **Настройки → Аккаунты → GitHub:** аватар, логин, «Отключить».
- **Главная:** кнопка «Клонировать с GitHub» рядом с «Новый» и «Импорт».
- **В проекте:**
  - значок ветки в верхней панели (`main ↑2 ↓1`) показывает, сколько изменений не отправлено и не получено;
  - лист «GitHub»: «Получить», «Отправить…», «Открыть на github.com», «Опубликовать сайт».
- **В дереве файлов:** точки у изменённых файлов, как в VS Code: M — изменён, A — новый, D — удалён.
- **Без сети:** работа продолжается как сейчас, счётчик ↑ растёт, отправка доступна позже.

## Безопасность и App Store

- **Guideline 2.5.2.** Скачанный код запускается в той же песочнице, что и сейчас: Pyodide и php-wasm в воркерах, предпросмотр в изолированном iframe. Приложение не меняет собственную функциональность, так что это тот же «редактор/обучение», что уже на ревью. В заметках для ревью нужно описать GitHub-сценарий и дать тестовый аккаунт GitHub с одним репозиторием (иначе ревьюер не сможет проверить вход).
- **4.8 (Sign in with Apple).** Не требуется: GitHub — подключение стороннего сервиса для работы с ним, а не вход в наш аккаунт.
- **5.1.1(v) (удаление аккаунта).** Не требуется: мы не создаём аккаунтов. Есть «Отключить».
- **App Privacy.** Разработчик не получает доступа к данным, но в анкете честнее отметить «User Content» → «App Functionality», не связанный с отслеживанием. Перед релизом нужно сверить с актуальными формулировками Apple. Политику дополнить.
- **Секреты в проектах.** Перед push показываем предупреждение, если в изменениях есть `.env`, `*.pem`, `id_rsa` или строки, похожие на ключи (`ghp_…`, `sk-…`, `AKIA…`). Поддерживаем `.gitignore`: файлы из него не отправляются.

## План по этапам

| Этап | Что входит | Оценка |
|---|---|---|
| 0. Прототип | Device Flow + Keychain-плагин + `GET /user`; проверка refresh для GitHub App на устройстве | 2–3 дня |
| 1. Клонирование и pull только для чтения | Выбор репозитория, zipball-импорт, `baseTree`, «Получить» без конфликтов | 1 неделя |
| 2. Push | Экран коммита, Git Data API, 422 → pull, `.gitignore`, проверка секретов | 1 неделя |
| 3. Конфликты | Трёхстороннее сравнение, построчный diff, выбор версии | 1 неделя |
| 4. Pages и новый репозиторий | Публикация сайта, создание репозитория | 3–4 дня |
| 5. Дальше | Ветки (создать и переключить), Pull Request из ветки, статус GitHub Actions, Gist для одиночного файла | по запросу |

Тесты:
- unit: blob SHA-1, трёхстороннее сравнение и `.gitignore` на фикстурах;
- E2E: мок GitHub API через Playwright `route()`;
- ручной сценарий на тестовом аккаунте: клонировать, правка на телефоне и на github.com, конфликт, разрешение, push, Pages.
